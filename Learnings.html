Chapter 1D States - L States

Device and Link Power States: D-States and L-States Relationship Guide

1.1 Introduction

ACPI (Advanced Configuration and Power Interface) defines how firmware and the operating system coordinate power management.

For PCIe/CXL power behavior, two state families are commonly discussed:

  • D-states: device or function power states
  • L-states: link power states

1.2 What D-States Mean

D-states describe the power and functional readiness of a device function.

Basic Definitions

This section provides the basic D-state meanings.

  • D0: Fully active and working. The device is powered and ready for normal use.
  • D1: Light low-power state. Lower power than D0, usually quicker to return than deeper states.
  • D2: Deeper low-power state than D1. Typically saves more power but may take longer to resume.
  • D3hot: Deep low-power state where the device is not fully operational, but can still remain logically present.
  • D3cold: Deepest device state where main power can be removed. Device context may be lost and re-initialization is often required.

1.3 What L-States Mean

L-states describe PCIe link activity between two components, not the device function's internal power state.

Common states:

  • L0: active link
  • L0s: shallow link idle state (PCIe) - Tx and Rx clock PLLs are on but might lose sync
  • L1: deeper link idle state - Tx and Rx clocks may be off
  • L1.x: L1 substates with deeper savings
  • L2/L3 Ready and L3: progressively more inactive/off link behavior

1.4 Why D and L States Are Different but Coupled

Examples:

  • A function can remain in D0 while the link dynamically enters L1 through ASPM. (No need to enable D3 hot for ASPM L1 Test)
  • A function can be moved to non-D0 (for example D3hot), and link behavior can then transition to L1 due to PCI-PM rules. (Need to enable D3 hot for PM L1 Test)

So, the device can be "awake" while the link naps(ASPM L1), or the device can be demoted and the link follows a deeper policy(PM L1).

1.5 Practical Mapping Between Downstream D-State and Link Options

Practical mapping used in validation contexts:

  • Downstream in D0: link commonly allowed in L0, L0s, ASPM-L1, and L2/L3 Ready policy paths
  • Downstream in D1/D2/D3hot: link commonly allowed in L1 family and L2/L3 Ready policy paths
  • Downstream in D3cold: link tends toward L2/L3 classes depending on aux power and platform design

Interpretation:

As downstream device power gets deeper, permissible or expected link behavior usually becomes more aggressive.

1.6 Two Distinct Ways a Link Reaches L1

L1 can be reached by two different mechanisms. These should be tested separately.

1.6.1 ASPM-directed L1

  • Device remains in D0.
  • Hardware autonomously enters L1 when traffic is idle.
  • Hardware autonomously exits to L0 when traffic resumes.

This is active-state link power management.

1.6.2 PCI-PM-directed L1

  • Software programs device function to non-D0 (D3hot).
  • Link transitions to L1 as part of PM-directed behavior.

This is software-directed device PM influencing link PM.

1.7 ASPM-L1 vs PM-L1 Validation Focus

ASPM-L1 validates:

  • link capability advertisement and negotiation
  • link-control programming for ASPM enablement
  • autonomous idle entry and wake exit latency
  • functional continuity while device remains in D0

PM-L1 validates:

  • PMCSR or equivalent PM programming
  • device transition to non-D0
  • link response to PM-directed transition
  • suspend/resume correctness and wake policy behavior

1.8 Relationship to ACPI Methods and Objects

ACPI methods used around D-states:

  • _PS0/_PS1/_PS2/_PS3: request D-state transitions
  • _PSC: report current D-state
  • _SxD and _SxW families: describe system-state relationships and wake depth support
  • _DSW: arm/disarm wake with target S-state and D-state context

Important:

ACPI describes policy intent and platform controls. The actual link behavior still depends on bus-level mechanisms (ASPM, PCI PM registers, and controller/port implementation).

1.9 Bus Hierarchy Effects

For PCIe hierarchies, parent/child ordering matters:

  • Downstream endpoints are typically transitioned before upstream bridges/ports during power-down.
  • Resume generally progresses from upstream toward downstream.

This ordering is required so link and function dependencies remain valid.

1.10 PCIe and CXL View of L0 to L1

1.10.1 PCIe endpoint

  • L0 to L1 can occur by ASPM (idle, D0 retained) or by PM-directed non-D0 transition.

1.10.2 CXL endpoint (high-level)

  • CXL.io is PCIe-based for link PM but can have mode-specific constraints.
  • Some CXL modes (for example certain RCD/eRCD contexts) may use ASPM-L1 behavior while limiting or not requiring PCI-PM-directed L1 behavior.
  • CXL.cache/CXL.mem behavior is coordinated through CXL mechanisms (such as ARB/MUX [arbiter/multiplexer logic that selects and coordinates protocol traffic] and ALMP signaling paths [link-management messages used to coordinate low-power transitions]) and is not identical to classic PCIe PM-directed sequencing.

Chapter 2Power Management States: P-States, C-States, and Package C-States

2.1 Introduction

Modern CPUs do not run at one fixed power level all the time. They continuously change performance and idle depth to balance three goals:

  • performance
  • power consumption
  • temperature

Three major concepts are used for this control:

  • P-states: active performance states
  • C-states: core idle states
  • package C-states: whole-package idle states

A simple way to remember this is:

  • P-states answer, "How fast should active work run?"
  • C-states answer, "How deeply can an idle core sleep?"
  • Package C-states answer, "How deeply can the entire CPU package sleep?"

2.2 Big Picture Difference

P-states and C-states are not the same kind of state.

P-states apply while the core is doing work. They tune voltage and frequency to match workload demand.

C-states apply when the core is idle. They shut down parts of the core to save power.

Package C-states are deeper platform-level idle states entered only when conditions across the whole package allow it.

2.3 P-States Basics

P-states are performance states used when a core is active.

In traditional naming:

  • P0 is highest performance
  • P1, P2, P3, and so on are lower performance points

As P-state number increases, frequency usually decreases and power usage usually drops.

2.3.1 What Changes Across P-States

When moving between active performance states, the system adjusts:

  • core frequency
  • operating voltage (depending on architecture and control mode)
  • sometimes power limits and boost behavior interactions

The target is to provide only as much performance as needed for current load.

2.3.2 Why P-States Matter

P-state control helps with:

  • reducing average power under light or moderate load
  • controlling temperature
  • extending battery life in mobile systems
  • allowing better power budget distribution in server platforms

If load rises quickly, the CPU can request a higher performance point. If load drops, it can back off to save power.

2.4 P-States and Turbo Behavior

Turbo and boost behavior are related but not identical to classic fixed P-state tables.

In many modern systems:

  • the operating system provides performance intent
  • hardware power control chooses exact frequency in real time
  • boost may push above base operating points if power and thermal limits allow

This means practical frequency behavior can be dynamic and not a simple fixed step sequence.

2.5 C-States Basics

C-states are idle states for a core.

If a core has no work to execute, it can enter an idle state. Deeper idle states save more power but take longer to wake.

Common conceptual mapping:

  • C0: core is active and executing instructions
  • C1: shallow idle, very fast wake
  • C3, C6, C7 and deeper: more internal blocks are gated or powered down

Exact names and behavior vary by microarchitecture, but the general rule is consistent:

Deeper C-state means:

  • lower idle power
  • higher entry and exit latency

2.6 Core C-State Tradeoff

C-state control is always a latency-versus-power tradeoff.

Shallow states:

  • lower power savings
  • faster wake

Deep states:

  • higher power savings
  • slower wake

Good policy tries to choose the deepest state that still meets response-time requirements.

2.7 Package C-States Basics

Package C-states are idle states of the entire CPU package, not just one core.

A package can enter deep package idle only when broader conditions are met, usually including:

  • all or most cores are in sufficiently deep core idle states
  • uncore activity is low enough
  • interrupts and pending work allow entry
  • platform conditions and policies allow deeper package residency

Examples are often named as package C2, package C6, package C10, and similar, depending on platform generation.

2.8 Why Package C-States Are Important

Package C-states are critical for system-level idle power.

Core C-state entry alone may not deliver best idle power if uncore and package-level domains remain active. Deep package residency usually brings much larger total power reduction.

This is especially important for:

  • idle desktop and mobile efficiency
  • server idle power
  • thermal management in low-utilization periods

2.9 Relationship Between P-States, C-States, and Package C-States

These states interact but represent different dimensions.

When workload is active:

  • P-state behavior dominates
  • cores stay in C0 more often
  • deep package C-state residency is limited

When workload is bursty or idle:

  • cores spend more time entering core C-states
  • package may accumulate residency in deeper package C-states
  • average power drops significantly

A useful mental model is:

  • P-state is "active efficiency"
  • C-state is "core idle efficiency"
  • package C-state is "whole-socket idle efficiency"

2.10 Who Controls These States

Control is shared across multiple layers:

  • hardware power control logic
  • firmware and BIOS settings
  • operating-system power policy
  • scheduler behavior and interrupt activity
  • device and driver behavior

This is why two systems with the same CPU may show different residency and power numbers under similar workload.

2.11 Typical BIOS and Policy Knobs

Common controls you may see in platform setup and policy include:

  • hardware-managed P-state enable options
  • energy-performance preference controls
  • C-state enable or disable options
  • package C-state limit settings
  • autonomous mode and governor-style policy selection

Changing these knobs can strongly affect:

  • performance consistency
  • wake latency
  • average power
  • thermal behavior

2.12 Common Validation Observations

In real validation, these patterns are common:

2.12.1 High Performance, Low Idle Depth

  • CPU remains in high performance points
  • deep C-state residency is low
  • package deep residency is low
  • power stays higher

2.12.2 Good Idle Entry but Poor Wake Sensitivity

  • deep C-state residency increases
  • wake latency events become more visible
  • workload responsiveness may degrade in latency-sensitive tests

2.12.3 Core C-States Present but Weak Package C-States

  • cores show idle entry
  • package deep state residency remains low
  • often indicates uncore or platform-level blockers

2.13 Typical Reasons Deep States Do Not Happen

If expected deep idle states are not reached, common reasons include:

  • background interrupts or timer activity
  • frequent periodic polling
  • device drivers preventing low-power entry
  • firmware settings limiting C-state depth
  • power policy configured for maximum performance
  • ongoing uncore or fabric activity

For package C-state issues specifically, package-wide conditions often block entry even when individual cores look idle.

2.14 Metrics to Watch During Analysis

Useful measurements include:

  • per-core C-state residency percentages
  • package C-state residency percentages
  • effective operating frequency under load
  • power and temperature trends
  • interrupt rates and wake events

You usually need both performance metrics and residency metrics. Looking at only one can lead to wrong conclusions.

2.15 Practical Debug Order

When behavior looks wrong, a structured order helps:

1. Confirm BIOS and policy settings for P-states and C-states.

2. Confirm OS power profile and governor-style behavior.

3. Check core C-state and package C-state residency counters.

4. Check active frequency behavior against workload level.

5. Look for periodic wake sources and interrupt-heavy components.

6. Check driver and device activity that may block idle depth.

7. Re-test with controlled workload to isolate policy versus hardware limits.

2.16 Quick Comparison

P-States:

  • applied during active execution
  • control performance and active power
  • higher performance points usually mean higher power

C-States:

  • applied when a core is idle
  • control per-core idle power
  • deeper states save more power but add wake latency

Package C-States:

  • applied at CPU package level
  • control whole-package idle power
  • deepest savings usually require broad platform quietness

2.17 Common Confusions

Confusion 1:

"If P-state is low, idle power must also be low."

Not always. P-states help during active operation. Deep idle power mainly depends on C-state and package C-state residency.

Confusion 2:

"Core C-state entry guarantees deep package state entry."

Not always. Package entry has additional package-level and platform-level conditions.

Confusion 3:

"Highest performance policy always means best user experience."

Not always. It can increase power and temperature and may reduce efficiency without meaningful benefit for some workloads.

Chapter 3MCTP

3.1 Introduction

MCTP stands for Management Component Transport Protocol. It is a DMTF-defined management transport protocol used for communication between management components and managed devices.

The easiest way to understand MCTP is to think of it as a standard transport layer for management traffic. It gives devices and controllers a common way to exchange management messages even when the underlying physical transport is different.

MCTP is not usually the final protocol that carries the actual management meaning by itself. Instead, it often carries other protocols such as PLDM, SPDM, NVMe-MI, NC-SI, and vendor-defined messages.

3.2 Important Acronyms and Terms

Before learning the packet details, it is important to understand the main terms used in the MCTP ecosystem.

  • MCTP: Management Component Transport Protocol
  • DMTF: Distributed Management Task Force
  • NC-SI: Network Controller Sideband Interface
  • PT: Pass Through traffic
  • PLDM: Platform Level Data Model
  • RDE: Redfish Device Enablement
  • SPDM: Security Protocol and Data Model
  • PECI: Platform Environment Control Interface
  • PMT: Platform Monitoring Technology
  • NVMe-MI: NVMe Management Interface
  • CTA: Converged Telemetry Architecture
  • CTF: Converged Telemetry Framework
  • RMII: Reduced Media Independent Interface
  • BO: Bus Owner
  • VDM: Vendor Defined Message
  • VMD: Volume Management Device
  • VROC: Virtual RAID on CPU
  • CR DIMM: Crystal Ridge DIMM
  • NVDIMM: Non-volatile DIMM

These terms matter because MCTP is part of a larger manageability environment. It interacts with BMCs, storage devices, NICs, security protocols, telemetry flows, and platform-specific routing components.

3.3 What MCTP Is

MCTP defines a communication model for management traffic.

This communication can happen between:

  • management controller to management controller
  • management controller to managed device

MCTP includes several important parts:

  • message format
  • transport description
  • message exchange behavior
  • configuration and initialization messages

The key concept is that MCTP standardizes how management messages are addressed, routed, and delivered. This allows different components to communicate in a consistent way.

3.4 MCTP Topology Concepts

To understand MCTP properly, you need to understand how devices are organized in an MCTP network.

3.4.1 MCTP Network

An MCTP network is a logical collection of connected MCTP-capable buses and devices. Within this network, messages can be moved according to MCTP routing rules.

3.4.2 MCTP Bridge

An MCTP bridge connects two or more MCTP buses and routes packets between them. A bridge is important when management traffic must move across multiple bus segments or device groups.

3.4.3 Bus Owner

The Bus Owner is responsible for assigning Endpoint IDs, or EIDs, to devices on a bus. The topmost bus owner provides the EID pool that may be used for downstream assignment.

This means the Bus Owner handles identity management in the MCTP network.

3.4.4 Endpoint and EID

An endpoint is a device or function that terminates the MCTP protocol and handles MCTP control commands.

EID stands for Endpoint ID. It is the logical address used to identify and route messages to the correct MCTP endpoint.

The easiest way to connect these ideas is:

  • the bridge provides connectivity
  • the bus owner provides logical identity
  • the endpoint is the destination that actually handles the protocol

3.5 MCTP in Platform Context

MCTP is not used in isolation. It exists in a platform context with other protocols and interfaces.

Examples include:

  • PLDM for platform management operations
  • SPDM for security-related communication
  • NVMe-MI for storage-device management
  • NC-SI for network sideband control paths
  • PECI and PMT for Intel-specific management and telemetry usage

This matters because when you see MCTP traffic, the actual payload meaning usually comes from one of these higher-level protocols.

3.6 MCTP Packet and Transport Format

MCTP has a generic packet model, but the exact outer packet format depends on the transport binding.

3.6.1 Generic Packet Concept

At the core level, MCTP defines the message and routing behavior in a transport-independent way.

3.6.2 MCTP over PCIe VDM

One important transport is PCIe VDM. In this transport, the MCTP message is carried inside a PCIe vendor-defined message packet.

Important points from the page include:

  • PCIe VDM header fields matter for transport handling
  • data packet fields carry the MCTP content
  • message type identifies the payload protocol
  • routing rules depend on the PCIe VDM transport binding

Important field notes:

  • IC means Integrity Check indicator
  • for MCTP control messages, IC must be 0 according to the cited requirement
  • Message Type identifies what kind of payload is inside the MCTP message
  • PAD bytes may be used for alignment or format requirements

3.6.3 MCTP over SMBus or I2C

MCTP can also run over SMBus or I2C. The core meaning of MCTP stays the same, but the packet envelope changes.

This is an important learning point: MCTP semantics stay consistent, but the transport binding changes how the packet is wrapped and debugged.

3.7 Message Types Carried by MCTP

One of the most important parts of MCTP learning is understanding that MCTP carries different kinds of payloads. The Message Type field tells you what kind of payload is inside.

3.7.1 MCTP Control Messages, Msg Type 0x00

Control messages are the foundation of MCTP communication. They support discovery, addressing, control operations, and other basic protocol functions.

The page calls out:

  • request and response format
  • TO, Rq, and D bit usage
  • control command codes
  • completion codes

If control messaging is not working correctly, other higher-level MCTP traffic will usually fail as well.

3.7.2 PLDM over MCTP, Msg Type 0x01

PLDM is one of the main payloads carried over MCTP. It is commonly used for platform management functions such as inventory, sensors, configuration, and firmware-related flows.

The actual decode depends on PLDM type, command code, and completion code definitions from the PLDM specifications.

3.7.3 NC-SI over MCTP, Msg Types 0x02 and 0x03

NC-SI uses two distinct message classes over MCTP:

  • 0x02 for control packets
  • 0x03 for pass-through packets

This distinction matters during trace analysis because control traffic and pass-through traffic serve different purposes.

3.7.4 NVMe-MI over MCTP, Msg Type 0x04

NVMe-MI allows management access to NVMe devices through MCTP. This may include health, configuration, feature, and log access.

An important note is that request and response details vary by NVMe-MI opcode and subtype. You cannot assume one universal payload format for every NVMe-MI packet.

3.7.5 SPDM over MCTP, Msg Type 0x05

SPDM uses MCTP as a transport for security-related exchanges. These exchanges may include authentication, security negotiation, and secure session-related behavior.

This is the security-focused branch of MCTP usage.

3.8 Endpoint Discovery

The page states that PCIe MCTP endpoint discovery is handled through MCTP control messages, following the referenced transport-binding flow.

This matters because correct discovery is required before stable addressing and routing can work. If discovery is wrong, message delivery may fail even if the rest of the packet looks correct.

3.9 Main Use Cases of MCTP

The page describes MCTP usage across mobile, desktop, workstation, and server manageability scenarios.

Core use cases include:

  • protocol establishment and control setup
  • crash dump and log handling
  • configuration and register access
  • telemetry flows such as crashlog, aggregation, watcher, and stream behavior

Device classes mentioned include:

  • NICs and network adapters
  • storage devices
  • NVDIMMs
  • BMC

3.10 Software and Driver Dependencies

The page makes an important practical point: software stack support matters.

Protocol behavior cannot be judged only from packet format. Real deployment depends on the combined behavior of:

  • protocol implementation
  • firmware
  • device drivers
  • userspace tools or service layers

VROC and driver support are specifically called out as important in practical MCTP deployment.

The page collects several important standards references.

DMTF and related standards listed include:

Chapter 4ACS & Source Validation

Access Control Services (ACS) is a standard PCI Express capability designed to manage and restrict peer-to-peer communications within a PCIe fabric. Because standard PCIe configurations allow device-to-device communication, they present security and access control risks. ACS provides the necessary controls to limit which components are allowed to communicate with one another, ensuring hardware-level isolation and preventing unauthorized access or data leakage between devices.

ACS functionality is typically implemented in the transaction layer of PCIe root ports. It consists of several hardware-enforced checking mechanisms, which include Source Validation, Transaction Blocking, and Peer-to-Peer (P2P) Request Redirection

Source Validation is a specific security feature under the ACS umbrella.

When Source Validation is enabled on a PCIe Downstream Port, the hardware performs the following validation steps on incoming transactions :

  1. Bus Number Verification: The Downstream Port inspects the Requester ID (RID) of every upstream request it receives. It specifically looks at the Bus Number portion of that ID
  1. Aperture Testing: The port checks if this Bus Number falls within its designated bus "aperture". This aperture is the inclusive range of buses defined by two of the port's registers :
    • The Secondary Bus Number register
    • The Subordinate Bus Number register
  1. Violation Handling: If the Bus Number of the requesting device is outside of this designated aperture, the request is flagged as an ACS Violation error associated with the receiving port. If the Bus Number is within the aperture, the transaction is permitted to proceed.

Chapter 5MMIO

5.1 Definition

  • MMIO is a hardware communication method where the CPU interacts with peripheral devices using the standard physical address space.
  • Instead of pointing to system RAM, specific memory address ranges are routed directly to hardware registers or device memory (such as a GPU's VRAM).
  • Drivers interact with hardware by dereferencing standard software pointers to these physical addresses, using standard load and store instructions.

5.2 MMIO vs. Port I/O (PIO)

  • Address Space: PIO uses a separate, isolated address space (e.g., 64KB on x86). MMIO shares the massive, flat physical address space with system RAM.
  • Instructions: PIO requires special, restrictive assembly instructions (like IN and OUT). MMIO relies on standard memory access instructions, simplifying programming and improving performance.

5.3 Caching Rules

  • Caching must be disabled: Memory regions mapped for MMIO must be configured by the OS as uncached or strongly ordered.
  • If the CPU cached an MMIO address, it might optimize away sequential writes intended to trigger hardware actions, or it might read a stale hardware state from its local L1/L2 cache instead of querying the physical device for real-time status.

5.4 The PCIe Implementation

  • The Root Complex Translation: The CPU cores do not speak the PCIe protocol natively. When the CPU executes a memory write to an MMIO address, the CPU's memory controller routes it to the PCIe Root Complex. The Root Complex acts as a translator, taking the raw memory instruction and encapsulating it into a serial Transaction Layer Packet (TLP).
  • Device Enumeration and BAR Sizing: PCIe endpoints determine their own memory footprint needs using Base Address Registers (BARs). During system boot, the BIOS or OS writes all 1s to the BAR and reads it back; the device responds with a bitmask indicating how much contiguous memory space it requires (e.g., 4KB or 256MB). The OS then finds an available block in the global physical address map and programs the starting address into the BAR.
  • Packetized Transactions (TLPs): An MMIO write translates into a Memory Write (MWr) TLP, and a read translates into a Memory Read (MRd) TLP. These packets contain a header (with the target 32-bit or 64-bit physical address, packet length, and traffic class attributes) and the data payload itself.
  • Switch Routing via Base/Limit Registers: As a TLP travels away from the CPU, it may pass through PCIe switches. PCIe does not broadcast traffic. Instead, each downstream port on a switch contains internal Base and Limit registers. The switch examines the TLP's destination address, compares it against these registers, and routes the packet strictly down the port that claims that specific address range.

5.5 Posted vs. Non-Posted Transactions:

  • Writes are Posted: MMIO writes are "fire-and-forget." The Root Complex dispatches the MWr TLP and the CPU immediately resumes executing instructions without waiting for an acknowledgment. This prevents CPU stalls and maximizes throughput.
  • Reads are Non-Posted: MMIO reads require a round-trip. The Root Complex issues an MRd TLP, and the CPU must wait. The target endpoint processes the read and returns a separate Completion with Data (CplD) packet back up the tree. Because of this latency, MMIO reads are inherently much slower than writes and are used sparingly in high-performance drivers.

5.6 Relationship with System RAM

  • Data Storage: MMIO data is never stored in system RAM. The CPU's memory controller intercepts the specific address range and routes the transaction over the system bus directly to the hardware device.
  • Routing Maps: The physical map detailing which addresses go where is stored in the CPU's System Address Decoders (SAD) and the endpoint's BARs, not in RAM.
  • Virtual Memory Pages: The only aspect of MMIO stored in system RAM is the operating system's Page Tables. When a driver needs to access an MMIO device, the OS uses Page Tables in RAM to map memory-safe Virtual Addresses to the raw Physical MMIO Addresses.
